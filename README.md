# 推测解码验证台（Speculative Decoding Verifier）

用 FastAPI + CPU 版 PyTorch 实现的网页应用，包含两个彼此独立、共用同一套固定
权重模型的验证台：

1. **推测解码对照台（首页 `/`）**：验证推测解码能否在保证输出完全一致的
   前提下节省目标模型的前向调用，并验证被拒绝的草稿不会污染后续生成；
2. **受限续写验证台（`/constrained`）**：验证目标模型在「禁用片段规避 +
   指定尾句紧接 EOS 收尾 + 新 token 上限」三重约束下，能否按规定的受限贪心
   规则合法续写，并由独立无缓存逐步参考逐 token 核对后才展示。

所有模型权重在进程内以固定随机种子生成，**无需下载任何模型**；词表为固定的 98 个
字符级 token，草稿与目标模型共用。

## 目录结构

```
app/
  tokenizer.py       固定字符级词表（pad/unk/eos + 95 个可打印 ASCII，共 98 token）
  model.py           带 KV 缓存的小型因果 Transformer + 固定权重的草稿/目标模型
  decoding.py        无缓存逐 token 贪心基线 与 带 KV 缓存的推测解码
  constrained.py     受限续写：AC 禁用片段自动机 + 尾句 KMP + 可行性 DFS
                     + KV 主路径/无缓存参考双路径核对
  main.py            FastAPI 路由、序列化、固定预设、推理串行锁
static/
  index.html         推测解码单页前端
  constrained.html   受限续写单页前端（逐步候选/违规/死路/选中明细）

  test_decoding.py     推测解码 10 项关键功能测试

```

## 模型设计（均为固定权重、确定性可复现）

| 模型 | 层数 | 注意力头 | d_model | 说明 |
|---|---|---|---|---|
| 目标模型 | 4 | 4 | 128 | 被核验的大模型 |
| 草稿模型 | 1 | 2 | 128 | 提议草稿的小模型 |

- 二者**共享 token 嵌入与 LM head（权重绑定）**，词表共用；
- 草稿主体在同一初始化 RNG 流之后，再用独立固定种子（seed=99）注入受控高斯扰动
  （σ=0.125）。该尺度经实测使两模型首 token 预测翻转率约 30%，从而同一服务内
  既能稳定观测到**整块接受**，也能稳定观测到**拒绝**；
- 完全独立初始化会导致未训练模型 argmax 近乎 100% 不同（几乎全拒绝），完全一致
  又不会拒绝，受控扰动是让两条路径都可演示的关键。

## 推测解码算法要点

1. 用户设置每轮草稿数 `k ∈ [1,4]`、最多新 token 数 `max_new ∈ [1,32]`；
2. 每轮草稿模型基于**自身 KV 缓存**逐 token 增量写出最多 `k` 个草稿；
3. **目标模型每轮只做 1 次前向**，整块核验草稿；首轮输入「提示词+草稿块」，
   之后每轮输入「上一轮 pending 的纠正/补词 token + 新草稿块」，
   **已缓存前缀绝不重算**；
4. 逐位比对目标贪心预测与草稿 token：
   - 拒绝：丢弃被拒位置及之后的草稿，采用目标在该位置的纠正 token，并把目标/草稿
     KV 缓存截断回滚到接受前缀（回滚无污染，有专项测试）；
   - 整块接受：额外采用目标基于整块上下文的补词 token；
5. `max_new` 上限与 EOS 截断在两条路径上语义完全一致（EOS 计入输出，其后停止）；
6. argmax 平局取词表序号小者（`torch.argmax` 返回首个最大值，天然满足）。

**缓存不变量**：每轮开始时目标缓存覆盖确认前缀倒数第二个 token，pending 保存上一轮
tail；草稿缓存对齐完整确认前缀。因此目标前向次数恒等于推测轮数。

## 正确性保证

推测解码输出在拒绝、整块接受、EOS、达到上限等所有情况下，都与「目标模型**无缓存、
逐 token、对完整前缀重算**的贪心基线」**逐 token 完全相同**。前端在不一致时会标出
首个分歧位置（token id 与文本）并判定 FAIL。

## 受限续写验证台（`/constrained`）

### 输入约束（前后端双重校验）

| 字段 | 规则 |
|---|---|
| 提示词 | 1～32 个可打印 ASCII 字符（0x20～0x7E） |
| 禁用片段 | 1～3 条，每条 2～6 个可打印 ASCII 字符，不可重复 |
| 尾句 | 2～4 个可打印 ASCII 字符 |
| 新 token 上限 | 6～20，**EOS 计入上限** |

提示词自身已含禁用片段、或尾句自身含禁用片段时直接判定无解并返回中文原因。

### 受限贪心规则（每一步）

1. 候选集恒为 **95 个可打印 ASCII 字符 + EOS**（PAD/UNK 永不参与）；
2. 字符候选先过两道门：
   - **即时违规门**：用 Aho-Corasick 多模自动机检测追加后是否在生成文本或
     提示词-生成拼接处命中任一禁用片段（自动机状态只依赖最近 m-1 个字符，
     m 为最长片段长度 6，天然支持跨边界检测与状态记忆化）；
   - **可行性门**：对剩余预算做记忆化 DFS——从该候选的新状态出发，是否还能
     在剩余步数内以「完整尾句 + 紧接一个 EOS」合法结束；不能则该候选为死路；
3. EOS 仅在「已生成文本末尾完整匹配尾句」时合法（尾句匹配用 KMP 自动机，
   从生成起点计数）；
4. 在全部合法候选中取目标模型 **logit 最高**者，**平局取较小 token id**
   （屏蔽后张量 argmax 天然返回首个最大值）；
5. 主路径**复用目标模型 KV 缓存**：首轮一次灌入提示词，其后每步仅把实际选中的
   1 个 token 增量送入续算，绝不重算已缓存前缀。

### 双路径核对（只有完全一致才展示）

同一份候选/平局/可行性逻辑分别驱动两条前向路径：

- **主路径**：KV 缓存增量前向（首步输入 = 完整提示词，其后输入长度恒为 1）；
- **参考路径**：独立无缓存，逐步对完整前缀重算。

两者逐 token 比对：完全一致且独立的字符串级**终态合规复核**通过（无禁用片段、
尾句紧接 EOS、长度上限、EOS 唯一且在末尾）才返回续写；任何分歧返回
`verify_failed` 且**不展示任何部分结论**；两条路径一致判定无路可走时返回
`no_solution` 并说明卡在哪一步、剩余额度与尾句匹配进度。

### 与原解码的隔离

受限续写在模型状态快照/恢复保护下运行：返回后目标模型的权重（全程 `no_grad`
只读）、KV 缓存对象与长度、`forward_count` 与调用前完全一致；进程级推理锁
串行化所有请求。原推测解码的权重、KV 与前向计数不受新流程影响（有专项测试）。

### 接口

- `POST /api/constrained`：入参 `{prompt, forbidden[1..3], tail, max_new(6~20)}`；
  语义校验失败返回 400 + 中文原因；正常业务结果（含 `no_solution` /
  `verify_failed`）返回 200，载荷含状态、原因、逐 token 序列、逐步候选明细
  （合法/即时违规/死路/选中及 logit）、两条路径的目标前向次数、可行性查询次数
  与终态复核结论；
- `GET /constrained`：受限续写网页。

## 实测结果（CPU，torch 2.5.1+cpu，单线程）

### 推测解码（`python tests/test_decoding.py`，10 项全部通过）

- 84 组参数组合（7 提示词 × 4 个 k × 3 个 max_new）下，推测解码与贪心基线
  逐 token 完全一致；
- 缓存/无缓存两条前向路径的 argmax 决策逐位相同（logits 仅 ~1e-5 级 float32
  舍入差异）；缓存回滚后续写与整序列前向逐位一致；
- 前向次数（k=4、max_new=32）：
  - 整块接受预设：基线 **32** 次目标前向 → 推测 **7** 次（减少约 78%）；
  - 拒绝预设（首轮接受后持续被拒）：基线 32 次 → 推测 **28** 次，且输出仍与
    基线完全一致，证明被拒草稿不会污染后续生成；
- 强制注入 EOS 后，4 个 k × 3 个上限组合下两条路径 EOS 位置与截断完全一致。

> 说明：拒绝预设的前向节省为负向示例——当草稿质量差时推测解码不会节省调用，
> 这正是本验证台要展示的权衡；输出正确性不受影响。

### 受限续写（`python tests/test_constrained.py`，16 项全部通过）

- **Aho-Corasick 自动机**：500 组随机片段集（1～3 条、2～6 字符）+ 随机文本下，
  命中判定与朴素子串搜索完全等价；跨提示词边界命中、提示词前置命中均正确；
  自动机带「历史命中锁存」，片段在任意位置出现都永久判定违规；
- **尾句 KMP**：500 组随机尾句/文本下，匹配状态与朴素后缀语义逐位置一致；
- **可行性 DFS**：预算门控（尾句 L 字符 + EOS 需 L+1 个额度）与禁用片段绕行
  正确；紧预算实测（cap=6、尾句 4 字符）下第 1 步后每步 94 个字符被判死路、
  仅留唯一合法路径，最终恰好 `前缀字符 + 尾句 + EOS` 用满 6 个 token；
- **60 组随机端到端用例 + 3 组固定用例**：全部 `status=ok`，硬约束逐项成立
  （无禁用片段、拼接处无命中、尾句紧接 EOS、EOS 唯一且在末尾、EOS 计入上限、
  候选仅限可打印字符+EOS、主路径首步输入为完整提示词且其后恒为 1）；
- **双路径核对**：KV 主路径与无缓存参考逐 token 完全一致，两条路径目标前向
  次数均等于新 token 数；注入人为分歧时返回 `verify_failed` 且不返回任何
  续写内容；
- **状态隔离**：受限续写前后目标模型 KV 缓存对象/长度、`forward_count`
  完全不变，随后原推测解码的输出与前向计数与调用前逐 token 相同；
- **真实 uvicorn 冒烟**：`/api/constrained` 正常请求 200、语义校验失败 400、
  越界参数 422；跨边界禁用（提示词 `a` + 候选 `b` 命中 `ab`）实测被即时拦截；
  `/api/decode`、`/`、`/constrained` 均正常响应。

> 关于 `no_solution`：经分析，凡通过全部输入校验（含尾句不含禁用片段）的请求，
> 总能构造「单字符前缀 + 尾句 + EOS」合法路径，而每步可行性门控保证贪心不会
> 走入死路，因此公开 API 的有效输入恒有解；`no_solution` 分支由内部小预算等
> 防御场景的专项测试覆盖（含中途死路原因文案）。提示词/尾句自身含禁用片段的
> 静态无解在输入校验阶段即以 400 + 中文原因拦截。
